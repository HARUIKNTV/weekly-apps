# スマスロ沖ドキ！DUOアンコール 設定判別ツール

「沖ドキ！DUOアンコール」の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「設定判別・推測ポイント」](https://p-town.dmm.com/machines/4906#anc-point)（2026/09/06更新）に掲載されている判別要素をそのままの分類（ボーナステンパイ音／ボーナス中の楽曲変化）で反映し、実戦データと示唆演出の出現回数から設定期待度を算出します。

公開URL: https://haruikntv.github.io/weekly-apps/2026-09-10-okidoki-duo-encore/

## 一撃（1geki.jp）とのクロスチェック

[一撃「沖ドキDUOアンコール」設定差・設定判別要素まとめ](https://1geki.jp/slot/l_okidoki_duo_encore/0/)（2026/02/12更新）を確認したところ、掲載されている数値・示唆内容はDMMぱちタウンの内容と完全に一致していた。

- **ボーナス初当たり確率**（連チャン中を除く通算値）: 1geki側に設定1〜6（設定4を除く5段階）の完全なテーブルが掲載されており、DMM側の「通常AorB／引き戻し／チャンス」別テーブルと整合していたためこちらを採用（モード別テーブルはプレイヤーが滞在モードを正確に判別できないため不採用、詳細は下記）
- **チェリー確率**・**チェリー契機のボーナス当選率**: 両サイトで数値が完全一致（小数点まで同一）
- **ボーナステンパイ音の示唆**・**ボーナス中の楽曲変化「私バージョンアップ！」**: 両サイトで記載内容が完全一致

いずれの項目も両ソースで独立に裏付けが取れているため、そのまま採用した。

## 機能

- **数値データ**（①）: 「ボーナス初当たり確率・チェリー確率（総G数ベース）」と「チェリー契機のボーナス当選率（チェリー成立回数は上と共通）」の2系統を、それぞれ独立した二項尤度チャンネルとして入力可能
- **判別要素**（②）: ボーナステンパイ音（6種）、ボーナス中の楽曲変化（1種）の計7種類をDMMぱちタウンの分類のままカテゴリラベル付きでタップ式カウンターに記録
  - 金文字表示の「〜濃厚」は1回でも出現すれば矛盾する設定を候補から確実に除外
  - 斜体表示の「〜示唆」は確定情報ではないため、ハード除外はせず出現回数と強さに応じて参考程度の重みだけを加える
- 空欄の数値フィールドは「データなし」として扱い、そのチャンネルの計算をスキップ（0回出現と誤認しない`parseField`パターンを採用）
- タップ式のカウンターUI（コンパクトな一覧チップ表示でページを短く保つ）
- 数値データとカウント結果を組み合わせて、現在の有力候補と最有力設定をリアルタイム表示
- 広告枠（`.ad-slot`）を3か所設置：ヘッダー直下（728×90）、判別要素と結果の間（300×250）、フッター上（728×90）。今はプレースホルダー表示のみ（詳細はリポジトリルートのREADME「広告の設置について」を参照）
- サイト共通のフィードバックウィジェット（右下の💬ボタン、FormSubmit.co経由でメール操作不要のまま意見を送信）を搭載

## データについて（掲載を見送った項目とその理由）

DMMぱちタウン・1geki.jp双方のページを精読した上で、以下の項目は「掲載はあるが判別要素として採用しなかった」ものとして意図的に除外した。

- **設定4は非公開**: この機種は設定1・2・3・5・6の5段階設定で、両ソースの全テーブルが一貫して設定4の列を欠いている。別途Web検索で確認したところ、本機には「設定L」という下パネル消灯の特殊個体が存在し実質的に設定4相当の枠を担うが、その数値は非公開のため対象外とした（`SETTINGS = [1, 2, 3, 5, 6]`として実装）
- **モード別のボーナス当選率（通常A／通常B／引き戻し／チャンス）**: DMMぱちタウン自身が「滞在モードを正確に判別するのは難しいので、初当りの軽さで推測しよう」と明記しており、プレイヤーが実戦中にどの内部モードに滞在しているかを正確に見分けるのは非現実的。代わりに1geki.jpが公開している「ボーナス初当たり確率」（通算値）を採用した
- **スイカ契機のボーナス当選率**: DMMぱちタウンの本文に「スイカの当選率は全設定共通」と明記されており、設定差がないため判別要素にならない
- **ハイビスカスの点灯パターン／ドキハナモード関連の示唆／ボーナス終了画面の示唆／ボーナス入賞ラインの示唆／ハナちゃん＆カナちゃんランプ点灯／1G連濃厚パターンの演出法則**: いずれも内部モード（通常B以上・天国・ドキドキ・DUOモード・1G連など）を示唆する演出であり、設定そのものへの言及がないため対象外
- **ボーナステンパイ音のうち「ラッキー」「超ラッキー」「聴いてくれるかな…」「南野ハナ、歌いま～す」など**: モード（ドキドキ以上・超ドキドキ以上・キャラ楽曲）の示唆のみで設定への言及がないため対象外

## 技術メモ

[apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)のCSS・HTML骨格・JSアーキテクチャ（per-setting配列、`logBinomLikelihood`、`computeCandidateSettings`、`buildChips`、`render`、ソフトマックス正規化、フィードバックウィジェット）をベースに構築。

- 依存ライブラリなしの単一HTMLファイル（プレーンなHTML/CSS/JS）。ビルド不要で、そのまま静的ホスティング可能
- 設定4が存在しない5段階設定のため、[apps/2026-09-06-valvrave-2/](../2026-09-06-valvrave-2/)で採用した`SETTINGS`配列パターン（`const SETTINGS = [1, 2, 3, 5, 6]`、確率テーブルは設定番号をキーとするオブジェクト）を踏襲
- 空欄フィールドの安全な扱いは[apps/2026-09-07-monhun-rise/](../2026-09-07-monhun-rise/)の`parseField`パターンをそのまま採用: 空欄は`null`を返し、各チャンネルの尤度計算は対応する生の入力値が`null`でないことを個別にチェックしてから実行する。「チェリー成立回数」フィールドは①のチェリー確率チャンネルのk（総G数に対する分子）と、②のチェリー契機ボーナス当選率チャンネルのn（母数）の両方で共有・再利用している
- 尤度計算: 各チャンネルの二項分布`P(k|n,p)`の対数尤度を合算し、示唆要素は出現回数（上限3回でキャップ）×tier別の重み（弱0.2／通常0.35／強0.5）を加算。その後ソフトマックス的に正規化（一様事前分布を仮定）
- 判別要素は単一のデータ配列（`ITEMS`）で定義し、各項目の`kind`（hard/soft）と`cat`フィールドで確定/示唆の別とDMMの分類ラベルを保持。チップUIは`cat`が変わるタイミングで自動的にラベル＋新しい行を生成する
