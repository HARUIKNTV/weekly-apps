# スマスロうみねこのなく頃に2 設定判別ツール

「Lパチスロうみねこのなく頃に2」の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「設定判別・推測ポイント」](https://p-town.dmm.com/machines/4925)（2026/09/10更新）に掲載されている判別要素をもとに、実戦データと示唆演出の出現回数から設定期待度を算出します。2026年2月2日導入の機種で、判別データは実戦・調査に基づいたものが十分に公開されている状態でした。

公開URL: https://haruikntv.github.io/weekly-apps/2026-09-10-umineko2/

## 一撃（1geki.jp）とのクロスチェック

[一撃「うみねこのなく頃に2」設定差・設定判別要素まとめ](https://1geki.jp/slot/l_umineko2/0/)（2026/06/05更新）を確認したところ、掲載されている数値・示唆内容はDMMぱちタウンの内容と完全に一致していた。特に以下の点で1geki側の記述がDMM側の省略表記（設定差なしの列は初出のみ表示する形式）を補完し、各チャンネルが「設定1〜6の完全なテーブル」であることを確認できた。

- ボーナス合算確率・特定ボーナス合算確率（1geki側で設定1〜6の完全テーブルとして明記）
- 周期天井到達時の初期真実ポイント振り分け（DMM側は70pt列が省略されていたが、1geki側で「70pt: 12.5%固定・全設定共通」であることが確認でき、30pt/50pt/70pt/200ptの4区分がすべて完全と判明）
- ステージチェンジ時のロゴ発光パターン（発光［小］［大］の出現割合が設定1〜6で完全一致）
- ボーナス終了画面の示唆絵柄：DMM側は「BIG①〜⑤」という抽象的な画面ラベル、1geki側は「戦人一家」「ベアト・戦人①」などの具体的なキャラクター名で説明していたが、示唆内容（設定2以上濃厚／2･4･6濃厚／4以上濃厚／5以上濃厚／6濃厚）が完全に一致していたため、同一の演出を指しているものとして1つのカテゴリに統合した

## 機能

- **数値データ**（①）: ボーナス合算確率（総G数ベース）、1枚役B・1枚役C・確定役A（総G数は上と共通）、ART中の共通ベル・ハズレ確率（ART中の消化G数ベース）、RB中の斜め青7揃い、ステージチェンジ時のロゴ発光、周期（天井）到達時の初期真実ポイント、運命分岐モード転落時の引き継ぎゲーム数、BIG中のハズレ成立時ポイント獲得——全8系統をそれぞれ独立した二項尤度チャンネルとして入力可能。空欄の項目は「未入力」として扱い、その場のチャンネル計算をスキップする（0回成立と誤認しない）
- **判別要素**（②）: 運命分岐モード即転落時のボイス、メニュー「Story collection」全開放時の示唆、REG中のキャラ紹介の背景、ボーナス確定画面（ハロウィン）、通常時の超パー演出（ゾロ目％）、ボーナス終了画面の示唆絵柄、BIG中ビタ押し成功時の1枚絵――計37種類を、DMMぱちタウン・1geki双方の分類を統合したカテゴリラベル付きで1つのリストにまとめてタップ式カウンターで記録
  - 金文字表示の「〜濃厚」は1回でも出現すれば矛盾する設定を候補から確実に除外
  - 斜体表示の「〜示唆」は確定情報ではないため、ハード除外はせず出現回数と［弱/通常/強］の強さに応じて参考程度の重みだけを加える
- タップ式のカウンターUI（コンパクトな一覧チップ表示でページを短く保つ）
- 数値データとカウント結果を組み合わせて、現在の有力候補と最有力設定をリアルタイム表示
- 広告枠（`.ad-slot`）を3か所設置：ヘッダー直下（728×90）、判別要素と結果の間（300×250）、フッター上（728×90）。今はプレースホルダー表示のみ（詳細はリポジトリルートのREADME「広告の設置について」を参照）
- 右下floatingの「💬」ボタンからご意見・ご要望を送信できるフィードバックウィジェットを搭載（FormSubmit.co経由、メールクライアント不要）

## データについて

以下は調査の過程で見つかったものの、今回は採用を見送ったデータ・演出。

- **LV2ナビ発生率（同色BB後／異色BB後／その他）**: 設定1〜6の完全な数値テーブルが公開されているが、直前の当選ボーナス種別（同色BB後・異色BB後・その他）ごとに条件分岐する3種の独立したチャンネルとなり、実戦中の記録が煩雑になりすぎるため、今回のツールでは見送った（データが不完全だからではなく、UIの複雑化を避けるための判断）
- **共通②「設定変更濃厚」・共通③「設定変更＋設定アップ濃厚」（終了画面）**: 特定の設定（1〜6のどれか）を示すものではなく「設定変更があったこと」自体を示す演出のため、設定1〜6の期待度を算出する本ツールの趣旨に合わないと判断し、チップには含めなかった
- **ボーナス終了画面「夜背景+縁寿」（設定変更濃厚）・「ベアト見下ろし」（設定上げ濃厚）**: 同様に特定設定を示すものではなく「変更・アップの有無」を示す演出のため見送った
- **2択ベル・スイカA・スイカB・1枚役Aなど**: DMM/1geki双方で「設定差なし」と明記されている小役のため、判別要素としては採用していない（数値としては公開されているが、設定を区別する情報を持たないため）

いずれも「設定によって欠落している値がある」ために見送ったものではなく、採用した全チャンネルは設定1〜6について完全なデータが公開されていることを確認済み。

## 技術メモ

- 依存ライブラリなしの単一HTMLファイル（プレーンなHTML/CSS/JS）。ビルド不要で、そのまま静的ホスティング可能
- UIのCSS・HTMLスケルトン・JS計算ロジック（`logBinomLikelihood` / `computeCandidateSettings` / `buildChips` / `render` とソフトマックス正規化、および右下のフィードバックウィジェット）は [apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/) をベースに作成
- 空欄フィールドの安全な扱い（`parseField`ヘルパーでblankを`null`として扱い、各チャンネルは自分自身のフィールドがnullでない場合のみ計算する）は [apps/2026-09-07-monhun-rise/](../2026-09-07-monhun-rise/) の`render()`実装パターンを踏襲
- 尤度計算: 各チャンネルの二項分布 `P(k|n,p)` の対数尤度を合算し、示唆要素は出現回数（上限3回でキャップ）×tier別の重み（弱0.2／通常0.35／強0.5）を加算。その後ソフトマックス的に正規化（一様事前分布を仮定）
- 判別要素は単一のデータ配列（`ITEMS`）で定義し、各項目の`kind`（hard/soft）と`cat`フィールドで確定/示唆の別とカテゴリラベルを保持。チップUIは`cat`が変わるタイミングで自動的にラベル＋新しい行を生成する
- 今回のデータはDMMぱちタウン・1geki双方とも設定1〜6が完全に揃っていたため、`SETTINGS`配列によるオブジェクトキー方式（欠落設定を除外するパターン）は不要と判断し、従来通り`[1, 2, 3, 4, 5, 6]`の固定配列を使用している
