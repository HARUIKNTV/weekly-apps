# 炎炎ノ消防隊2 設定判別ツール

「Lパチスロ 炎炎ノ消防隊2（スマスロ）」の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「設定判別・推測ポイント」](https://p-town.dmm.com/machines/4926#anc-point)（2026/09/06更新）に掲載されている判別要素をそのままの分類（ボーナス終了画面／REG中のキャラ紹介／エンディング／獲得枚数表示）で反映し、示唆演出の出現回数から設定期待度を算出します。

公開URL: https://haruikntv.github.io/weekly-apps/2026-09-06-enen-shouboutai-2/

## 機能

- **数値データ**（①）: 炎炎ループ初当たり確率・ボーナス初当たり確率（一撃調べ）を独立した二項尤度チャンネルとして入力可能
- **判別要素**（②）: ボーナス終了画面の設定示唆画面、REG中のキャラ紹介（シナリオ・まもるくんの出現順・特定濃厚キャラ）、エンディングのミニキャラ、獲得枚数表示のすべての要素を、DMMぱちタウンの分類のままカテゴリラベル付きで1つのリストにまとめてタップ式カウンターで記録
  - 金文字表示の「〜濃厚」「〜否定」は1回でも出現すれば矛盾する設定を候補から確実に除外
  - 斜体表示の「〜示唆」は確定情報ではないため、ハード除外はせず出現回数と強さに応じて参考程度の重みだけを加える
- 広告枠を3か所設置（ヘッダー直下728×90、判別要素と結果の間300×250、フッター上728×90）— プレースホルダー表示のみ
- モバイル表示時の日本語の不自然な改行を防ぐCSS（`word-break: keep-all`）を適用

## 一撃（1geki.jp）とのクロスチェック（2026-09-07）

[一撃「炎炎ノ消防隊2」設定差・設定判別要素まとめ](https://1geki.jp/slot/l_ennenn2/0/)（2026/02/04更新）を確認したところ、DMMぱちタウンには掲載されていなかった**炎炎ループ初当たり確率**（設定1: 1/684 〜 設定6: 1/486）と**ボーナス初当たり確率**（設定1: 1/272 〜 設定6: 1/227）という2つの数値テーブルが新たに見つかったため、①数値データのカードを新設して追加した。判別要素（チップ）側に新規追加できるものはなかった。

## 数値データの細分化（2026-09-08）

スマスロ東京喰種の設定判別ツールで行った「数値データの細分化」（`field-group-label`の分離漏れ・未採用の完全な数値テーブルの追加）と同じ観点で、DMMぱちタウン「炎炎ノ消防隊2」設定判別・推測ポイント（2026/09/06更新、全文）と一撃「炎炎ノ消防隊2」設定差・設定判別要素まとめ（2026/02/04更新、全文）を再度読み直したが、**今回は数値チャンネル・判別要素チップともに追加すべきものが見つからなかった**。理由を以下にまとめる。

- **①数値データカードの配線チェック**: `numericInputs`配列（`totalG`/`enenLoopK`/`bonusK`）→ イベントリスナー（`numericInputs.forEach((el) => el.addEventListener('input', render))`）→ `render()`内の分割代入、の3点は東京喰種で見つかった配線漏れバグと同じパターンで確認したところ、すべて正しく接続されていた。
- **`field-group-label`の分離要否**: 現在①は「炎炎ループ初当たり確率／ボーナス初当たり確率」という1つの見出しの下に2つの数値（`enenLoopK`・`bonusK`）をまとめているが、これは東京喰種の裏AT（直行／100G以内／200G以内）のように**母集団（分母のN）が異なる別々の抽選を1つの見出しに混ぜてしまっていたバグ**とは事情が異なる——炎炎ループとボーナスはどちらも同じ「総G数」を分母とする初当たり系の確率であり、東京喰種側でも同様に「CZ・エピソードボーナス（総G数ベース）」の見出し1つの下にレミニセンス・大喰いの利世・エピソードボーナスの3チャンネルをまとめている（総G数が共通なら1見出しにまとめる、というのが両ツール共通のパターン）。よって分離は不要と判断し、見出しは変更していない。
- **DMMぱちタウンの判別要素チップの再確認**: 「設定推測要素まとめ」以下の「特定パターンの示唆」「ミニキャラの示唆」「特定の獲得枚数表示の示唆」に列挙されているすべての項目（ボーナス終了画面B〜F、第8/伝導者シナリオの特定パターン、まもるくんの出現順、紅丸・金シンラ・ショウ・黒野・ジョーカー・シンラ（死ノ圧）、エンディングのミニキャラ7種、獲得枚数表示4種）を1行ずつ既存の`ITEMS`と突き合わせたところ、**すべて既に登録済み**で漏れは無かった。
- **見つかったが数値チャンネルとして採用しなかった完全なテーブル**（理由付き）:
  - **ボーナス終了画面振り分け（非カスタム時）**: B画面・C画面はREG/アクセル/灰焰ボーナス後と炎炎ボーナス後で別々の設定1〜6完全テーブルが公開されている。しかし本ツール（および参照実装の東京喰種ツール）では「終了画面・キャラ紹介・獲得枚数表示」系の示唆はすべて`ITEMS`のタップ式カウンター（見た目の出現有無ベース）で扱う設計に統一しており、二項尤度の数値チャンネルは「レア役契機の当選率」のようなゲーム性側の抽選にのみ用いている。同じB画面・C画面の出現をチップと数値チャンネルの両方でカウントすると同一証拠の二重計上になってしまうため、既存のB画面／C画面チップ（設定4〜6示唆）を数値テーブルに置き換えることはせず、既存のまま維持した。またD・E・F画面は非カスタム時テーブルの値が既存チップの設定範囲（4以上濃厚／5以上濃厚／6濃厚）とちょうど一致しており、対象設定内では常にほぼ同じ数値（差が無い）ため、数値化しても新しい情報は増えない。
  - **REG中のキャラ紹介：シナリオ振り分け（第8／アイリス／伝導者／大隊長）**: 設定1〜6完全テーブルではあるが、4カテゴリ×複数パターンの多項分布であり、単純な二項尤度チャンネルに落とし込むと相互排他性を壊してしまう。またカテゴリ単位で集計しても設定に対して単調な傾向が弱く（例: 第8シナリオの選択率は設定1〜6で58%→60.5%→48%→59.5%→46.5%→52%とほぼ横ばいでノイズが大きい）、DMM自身が「特定パターンの示唆」としてまとめた個別キャラ・パターン単位のほうが有用な情報を保持している。そちらは前述の通りすでに`ITEMS`に反映済みのため、生テーブルの追加採用は見送った。
  - **金のランダムキャラ出現率（黒野／ジョーカー／シンラ（死ノ圧））・特定の獲得枚数表示出現率**: いずれも既存チップの設定範囲（4以上濃厚・5以上濃厚・6濃厚など）と完全に一致し、対象設定内での出現率はほぼ同一値（約1%）なので、数値チャンネル化しても既存チップ以上の情報は得られない。
  - **小Vリプレイの十字目変換発生率＆期待度**: 前回チェック時と変わらず、設定1と「高設定（設定4以上!?）」の2グループのみで設定2・3・5・6が不明かつ「!?」で閾値も曖昧なため、誤った補間を避けて引き続き未採用とした。
  - **一撃側**: 「終了画面」「RB中のキャラ紹介」のセクションは実戦画像のみで新たな数値テーブルは掲載されておらず、既存の炎炎ループ初当たり確率／ボーナス初当たり確率の2テーブル以外に追加すべきものは無かった。

結論として、今回の再チェックでは既存実装（数値チャンネル2種＋判別要素チップ全種）がすでに両サイトの内容を過不足なく反映していることを確認した。コード変更は行っていない。

## 数値データについて

DMMぱちタウン「設定判別・推測ポイント」内には、他機種にあるような単純な設定1〜6の数値テーブル（CZ確率など）が見当たらなかったため、判別要素（チップ）のみで構成していたが、一撃（1geki.jp）側で上記2テーブルが見つかったため現在は①数値データのカードも存在する。「小Vリプレイの十字目変換発生率＆期待度」は設定1と「高設定（設定4以上!?）」の2グループしかデータがなく、設定2・3・5・6の個別値が不明なため、誤った補間を避けるためにあえて未使用としている。

## 技術メモ

- 依存ライブラリなしの単一HTMLファイル（プレーンなHTML/CSS/JS）。ビルド不要で、そのまま静的ホスティング可能
- 「まもるくんが1〜5番目に出現→該当設定否定」は、記事本文の「出現した順番の設定を否定（1番目に出れば設定1否定）」というルール説明から、2〜5番目についても同様のパターンとして構成した
- チップUI・尤度計算の実装パターンは[スマスロ東京喰種 設定判別ツール](../2026-09-06-tokyo-ghoul-slot-checker/)を参照実装として踏襲
