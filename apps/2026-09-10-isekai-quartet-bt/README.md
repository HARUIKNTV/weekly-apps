# A-SLOT+ 異世界かるてっと BT 設定判別ツール

「A-SLOT+ 異世界かるてっと BT」（サミー製・2026年4月6日導入、設定1・2・5・6の4段階設定）の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「設定判別・推測ポイント」](https://p-town.dmm.com/machines/4965#anc-point)（2026/09/08更新）と[一撃「異世界かるてっと（スロット）」設定差・終了画面やキャラ紹介](https://1geki.jp/slot/l_isekai_quartet/0/)（2026/05/18更新）の両方を全文確認したうえで、公開されている判別要素をDMMぱちタウンの分類順（BIG・うわのせチャンス終了画面→サミートロフィー→獲得枚数表示→いせかるボーナス中のキャラ紹介→通常時のBIG直撃）のまま反映し、実戦データと示唆演出の出現回数から設定期待度を算出します。

公開URL: https://haruikntv.github.io/weekly-apps/2026-09-10-isekai-quartet-bt/

## 機能

- **数値データ**（①）: 以下4系統をそれぞれ独立した二項尤度チャンネルとして入力可能
  - **ボーナス初当たり・小役確率**（総G数ベース）：ボーナス初当たり、ベル、スイカ（弱・強合算）、チェリーの4チャンネル
  - **いせかる目・特殊15枚役・BB直撃率**（総G数は上と共通）：いせかる目成立、特殊15枚役、通常時BB直撃の3チャンネル（母数の総G数は同じ入力欄を再利用し、見出しのみ分離）
  - **BIG中のハズレ目（15枚役）出現率**（BIG中消化ゲーム数ベース。入賞時にリールフラッシュが出ないため実戦で判別しやすく、設定1の1/21845.3から設定6の1/512まで極端な設定差がある強力な判別材料）
  - **BT中の特殊7枚役出現率**（BT中消化ゲーム数ベース。いせかる目成立後・BT終了目次ゲームの確定払い出し分は除外してカウントする必要がある旨をヒント文で明記）
- **判別要素**（②）: BIG・うわのせチャンス終了画面（4種）、サミートロフィー（3色。本機は4段階設定のため銀・金トロフィーは出現しない）、獲得枚数表示（086枚OVERの同日3回目・4回目の追加濃厚パターンを含む5種）、いせかるボーナス中のキャラ紹介（通常示唆4種＋金3色の濃厚＋特殊シナリオ2種の計9種）、通常時のBIG直撃（単独赤7BIG／青7BIGの1種）——計21種類をDMMぱちタウンの分類のままカテゴリラベル付きで1つのリストにまとめてタップ式カウンターで記録
  - 金文字表示の「〜濃厚」は1回でも出現すれば矛盾する設定を候補から確実に除外
  - 斜体表示の「〜示唆」は確定情報ではないため、ハード除外はせず出現回数と［弱/強］の強さに応じて参考程度の重みだけを加える
- タップ式のカウンターUI（コンパクトな一覧チップ表示でページを短く保つ）
- 数値データとカウント結果を組み合わせて、現在の有力候補と最有力設定をリアルタイム表示
- 広告枠（`.ad-slot`）を3か所設置：ヘッダー直下（728×90）、判別要素と結果の間（300×250）、フッター上（728×90）。今はプレースホルダー表示のみ（詳細はリポジトリルートのREADME「広告の設置について」を参照）
- サイト共通のフィードバックウィジェット（右下の💬ボタン、FormSubmit.co経由でメール操作不要の送信）を同梱

## 一撃（1geki.jp）とのクロスチェック

DMMぱちタウンと一撃、両方のページを全文確認したところ、数値データ（ボーナス初当たり確率、小役確率、いせかる目当選率詳細、BB直撃当選率、BIG中のハズレ目出現率、BT中の特殊7枚役出現率）は両サイトでほぼ完全に一致していた（末尾の桁までピタリと一致する項目が大半）。判別要素（BIG終了画面の示唆、サミートロフィー、獲得枚数表示、いせかるボーナス中のキャラ紹介とその特殊シナリオ）も内容・示唆設定ともに完全に一致していた。

ボーナス初当たり確率の設定1〜6（実際は1・2・5・6）完全テーブルは一撃側にのみ掲載されており（DMMは機種概要欄に「ボーナス初当り確率は1/197.6（設定1）」と設定1のみ記載）、本ツールでは一撃の値を`P_BONUS_INITIAL`に採用し、コメントにその旨を明記した。逆にDMM側にのみ掲載されていたのが、単独赤7BIG／青7BIGの確率テーブルと通常時の赤7BIG・青7BIG比率（後述の通り、両方とも本ツールでは見送った）。

## データについて

以下は本文を確認したうえで、あえて数値チャンネル・判別要素チップのいずれにも採用しなかった項目とその理由。

- **通常時の赤7BIG・青7BIG比率**（両サイトに設定1・2・5・6の完全テーブルあり。青7BIG比率は56.8%→61.8%で高設定ほど優遇）：差が5ポイント程度と小さく、かつ「赤7BIG成立回数＋青7BIG成立回数」という専用の分母（BAR揃いBIGを除いた色7BIG回数）を新設する必要があり、既に採用しているいせかる目・小役系チャンネルと示唆の方向性が重複するため見送った。
- **スイカ＋青7BIG同時当選確率**（弱スイカ・強スイカ別、両サイトに完全テーブルあり）：「スイカとの同時当選時は青7BIG濃厚」という言及はあるが、出現頻度が1/16384〜1/5957.8と極めて希少で実戦データが集まりにくく、専用の分母を新設するほどの実用性がないため見送った（青7BIG成立自体は既存の数値チャンネルでは直接捕捉していないが、実質的な影響は小さいと判断）。
- **単独赤7BIG／単独青7BIG確率テーブル**（設定2以上でのみ出現、設定5・6でさらに優遇）：具体的な確率値は分母が数万単位と極端に大きく二項尤度チャンネルとしての実用性が低いため数値チャンネル化は見送ったが、「出現したら設定2以上濃厚」という濃厚要素としては②の判別要素チップに採用した。
- **リプレイ確率**：DMM本文に「通常時は、リプレイを除く全小役に設定差が存在」と明記されており、設定差がないため対象外。
- **BT中の小役確率（ボーナス成立前）・BT中のボーナス当選率（役ごと）**：両サイトとも「BT中の小役確率は全設定共通」「ベル約13%／スイカ約52%／チェリー約75%」のように設定に依存しない一律の値として記載されており、設定差データではないため対象外。
- **BAR揃いBIGの単独当選確率**：DMM本文に「単独BAR BIG確率は全設定共通」と明記されており対象外。
- **演出タイプ（体育祭／ツイン／愛／パトゆんゆん／盾／クラシック）とカスタムの内容**：いせかるチャンス中の告知方式の違いであり、設定差の記載がない純粋な演出バリエーションのため対象外。
- **BT中・状況ごとの小役確率の出目詳細（左1st／中1st／右1st別のリプレイ・ベルフラグ出目表）**：打ち方・目押し判別のための出目対応表であり、設定差データではないため対象外。

## 技術メモ

- 依存ライブラリなしの単一HTMLファイル（プレーンなHTML/CSS/JS）。ビルド不要で、そのまま静的ホスティング可能
- CSS・HTML骨格（`.card`／`.field-group-label`／`.chip`／`.bar-row`など）とJS設計（`logBinomLikelihood`／`computeCandidateSettings`／`buildChips`／`render`、ソフトマックス正規化）は[スマスロ東京喰種 設定判別ツール](../2026-09-06-tokyo-ghoul-slot-checker/)を参照実装としてCSS・フィードバックウィジェットを含め忠実に踏襲した
- 本機は設定3・4が存在しない4段階設定（1・2・5・6）のため、[革命機ヴァルヴレイヴ2 設定判別ツール](../2026-09-06-valvrave-2/)と同じ`SETTINGS = [1, 2, 5, 6]`配列＋設定値をキーとするオブジェクト（`P_X = { 1: ..., 2: ..., 5: ..., 6: ... }`）のパターンを採用。`computeCandidateSettings`・`render`とも配列インデックスではなく`SETTINGS`を介して設定値を扱う
- 尤度計算: 各数値チャンネルの二項分布 `P(k|n,p)` の対数尤度を合算し、示唆要素は出現回数（上限3回でキャップ）×tier別の重み（弱0.2／通常0.35／強0.5）を加算。その後ソフトマックス的に正規化（一様事前分布を仮定）
- 空欄安全性: [スマスロ モンスターハンターライズ 設定判別ツール](../2026-09-07-monhun-rise/)の`parseField`パターンを踏襲し、空欄は`null`（そのチャンネルをスキップ＝未入力）として扱い、「0」（確定0回）と区別している。各チャンネルは共有する総G数（またはBIG中／BT中ゲーム数）が入力済みかつ、そのチャンネル自身のk欄が空欄でない場合にのみ尤度計算へ加算する
- 判別要素は単一のデータ配列（`ITEMS`）で定義し、各項目の`kind`（hard/soft）と`cat`フィールドで確定/示唆の別とDMMの分類ラベルを保持。チップUIは`cat`が変わるタイミングで自動的にラベル＋新しい行を生成する
- `numericInputs`配列（要素の並び順）→ イベントリスナー（`numericInputs.forEach((el) => el.addEventListener('input', render))`）→ `render()`内の分割代入、の3点の並び順が一致していることを確認済み
