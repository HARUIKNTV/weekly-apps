# A-SLOT+ ディスクアップ ULTRAREMIX 設定判別ツール

「A-SLOT+ ディスクアップ ULTRAREMIX」（サミー、L DISCUPウルトラリミックスXR、2025年01月20日導入開始）の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「設定判別・推測ポイント」](https://p-town.dmm.com/machines/4702#anc-point)（2026/08/28更新）に掲載されている数値データと示唆演出の出現回数から、二項分布の尤度計算により設定期待度を算出します。

公開URL: https://haruikntv.github.io/weekly-apps/2026-09-10-disc-up-ultraremix/

## 機種の性格について（A-type + AT のハイブリッド）

本機はダンスタイム（DT）・DJゾーン（DZ）・ダンスタイムリミックス（DTR）というループ型ATを搭載しているが、実際に公開されている設定差データを見ると、判別の中心はBIG確率・REG確率・3枚役確率・スイカA確率・確定チェリー確率といった**独立した小役/ボーナス確率チャンネル**（古典的なA-typeの判別法）であり、ストーリー性のある専用の濃厚演出は「サミートロフィー」と「RB中の示唆演出」の2系統に限られる。そのため本ツールは①数値データを中心に据えつつ、②判別要素として2カテゴリ・計8個のチップを併設するハイブリッド構成にした（[apps/2026-09-10-my-juggler-5/](../2026-09-10-my-juggler-5/)の数値チャンネル中心の設計と、[apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)のチップリスト設計の両方を組み合わせている）。

## 機能

- **数値データ**（①）: 以下4系統・計10個の入力欄を、それぞれ独立した二項尤度チャンネルとして入力可能
  - 総G数を共通の分母とする、BIG当選回数・REG当選回数・3枚役（ボーナス/☆/☆）成立回数・スイカA成立回数・確定チェリー成立回数の5チャンネル
  - BB中・スイカ契機のULTRA上乗せ率（BB中のスイカ成立回数を分母とする独立チャンネル。設定1の1/16384.0から設定6の1/601.2まで約27倍の差がある強力な示唆要素）
  - リーチ目役T2成立時のBIG比率（ラッキーインフォで確認できるボーナスフラグの1つ。BIG比率が設定1の30.3%から設定6の19.3%まで低下し、裏を返せばREG比率が高設定ほど上昇する）
  - 空欄の項目は「データなし」として扱われ計算から除外される。0を入力した場合のみ「0回」として計算に反映される（`parseField()`によるnull安全設計）
- **判別要素**（②）: サミートロフィー（AT終了画面、銅/キリン柄/虹の3種）とRB中の示唆（演出モード共通で3種のモード全てに存在する「奇数/偶数示唆」「2以上/5以上/6濃厚」の5パターン）を、タップ式カウンターで記録
  - 金文字表示の「〜濃厚」は1回でも出現すれば矛盾する設定を候補から確実に除外
  - 斜体表示の「〜示唆」は確定情報ではないため、ハード除外はせず出現回数に応じて参考程度の重みだけを加える
- 数値データとカウント結果を組み合わせて、現在の有力候補と最有力設定をリアルタイム表示
- 広告枠（`.ad-slot`）を3か所設置：ヘッダー直下（728×90）、判別要素と結果の間（300×250）、フッター上（728×90）。今はプレースホルダー表示のみ（詳細はリポジトリルートのREADME「広告の設置について」を参照）
- 全ページ共通のフィードバックウィジェット（右下の💬ボタン、FormSubmit.co経由でメール操作不要）を搭載

## 一撃（1geki.jp）とのクロスチェック

[一撃「ディスクアップ（ウルトラリミックス）」設定差・設定判別要素まとめ](https://1geki.jp/slot/l_discup_ur/0/)（2025/12/09更新）を確認したところ、DMMぱちタウンと共通のデータソースに基づく内容で、以下の点を相互に検証できた。

- 一撃の「フラグ別ボーナス当選時のRB割合」表（設定1: 69.7% 〜 設定6: 80.7%）は、DMMぱちタウンの「フラグごとのBIG比率」表（リーチ目役T2、設定1: 30.3% 〜 設定6: 19.3%）と `100% − BIG比率 = RB割合` の関係で完全に一致した（例: 設定1は 100 − 30.3 = 69.7 ✓、設定6は 100 − 19.3 = 80.7 ✓）。この裏付けにより、採用したP_T2_BIGの値の信頼性を確認できた
- 一撃のRB中の示唆振り分け表（設定1/2/5/6の奇数・偶数・2以上・5以上・6濃厚の出現率）は、DMMぱちタウンに掲載されている3つの演出モード（REMIX/DISC UP/CLASSIC）それぞれの「示唆要素の振り分けまとめ」表と数値まで完全一致しており、「トータルの示唆振り分けは全モード共通」という記載を裏付けている
- 小役確率（リプレイ・3枚役・チェリー・スイカ合算）、BB中スイカでのULTRA上乗せ確率、確定チェリー確率も両サイトで数値が一致していた

## データについて

### 採用したデータ

- **BIG確率・REG確率**（設定別ボーナス確率表）
- **3枚役（ボーナス/☆/☆）確率**
- **スイカA確率**（スイカ合算ではなくスイカA単独の値を採用。理由は後述）
- **確定チェリー確率**
- **BB中・スイカ契機のULTRA上乗せ確率**（設定間で最大約27倍の差がある強力な示唆要素）
- **リーチ目役T2成立時のBIG比率**（ラッキーインフォで確認できるフラグの1つ。一撃のRB割合表と完全に整合することを確認済み）
- **サミートロフィー**（銅=2以上濃厚／キリン柄=5以上濃厚／虹=6濃厚）
- **RB中の示唆演出**（演出モード共通の奇数/偶数示唆、2以上/5以上/6濃厚）

### 見つけたが採用しなかったデータ（理由付き）

- **設定3・4のすべてのデータ**: DMMぱちタウン・一撃のいずれのページにも設定3・4の値は掲載されておらず（両サイトとも設定1・2・5・6の4列構成）、公開されている限り本機は現状これらの設定に対応する数値が存在しない。**CRITICAL RULE**により補間・推測はせず、`SETTINGS = [1, 2, 5, 6]`のオブジェクトキー方式で設定3・4を判別対象から完全に除外した
- **スイカB確率**: DMMぱちタウンの「スイカ確率詳細」表は設定1のみ「スイカA 1/59.6・スイカB 1/284.9」と両方を明示し、設定2/5/6は「スイカA」と「スイカ合算」の2値しか掲載していない。逆算すると（例: 設定2はスイカA 1/59.1・合算1/49.0 → 1/59.1 + 1/49.0の残差から求めたスイカB出現率が設定1のスイカB値とほぼ一致）、スイカBは全設定共通の固定値であることが確認できたため、設定差のあるスイカAのみを独立チャンネルとして採用し、スイカBおよびスイカ合算（Aと共通Bの合成値で、Aと重複情報になる）は不採用とした
- **確定3枚役確率**: 同様に設定1のみ「1/10922.7」の値が明示され、設定2/5/6欄には値が掲載されていない（＝全設定共通の固定値）。設定差がないため不採用
- **リーチ目役T3・A2・D2・G2、フラグD2のBIG比率/RB割合**: いずれも設定差のあるデータ自体は存在するが、出現率が1/1560〜1/16384とT2よりさらに稀な上、ラッキーインフォでの個別フラグ識別が必要になり実用上のハードルが高い。代表としてT2（最も出現頻度が高いフラグ）のみを採用し、他は判別要素を増やしすぎないよう見送った
- **REMIX/DISC UPモードの個別シナリオ表（36種・22種のパターン一覧）**: 「トータルの示唆振り分けは全モード共通」と明記されているため、3つのモードを別々にチップ化すると同じ統計的事象を3重にカウントしてしまう。1つの共通カテゴリにまとめることで二重カウントを回避した
- **ウルトラ高確移行率・転落率、DT/DZ/DTRの継続率、前兆ゲーム数振り分けなど**: 通常時・AT中で数値が異なる箇所はあるが、いずれのページにも設定差がある旨の記載がなく、設定判別要素としては不採用
- **技術介入（ビタ押し）精度ごとの機械割**: 遊技者の技術に応じた機械割の目安であり、設定差データではないため判別要素として使用していない

## 技術メモ

- [apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)の`<style>`ブロック（白・黒・赤基調のパレット）とHTML骨格（ヘッダー／広告枠／カード①②③／出典／免責事項／フッター、AdSenseスクリプトタグの位置を含む）、および末尾のフィードバックウィジェット（`.fb-fab`〜`</script>`）をそのまま踏襲した単一HTMLファイル。依存ライブラリなし、ビルド不要
- 設定3・4が存在しない4段階データの扱いは[apps/2026-09-06-valvrave-2/](../2026-09-06-valvrave-2/)の`SETTINGS = [...]`配列＋オブジェクトキー方式（`P_XXX[s]`）をそのまま採用。設定1〜6の固定配列インデックスは使わず、`SETTINGS.map((s) => ...)`で存在する設定だけを走査するため、欠落設定を誤って0扱い・補間することがない
- 尤度計算の空欄安全設計は[apps/2026-09-07-monhun-rise/](../2026-09-07-monhun-rise/)の`render()`にある`parseField(el)`パターンをそのまま採用。空欄は`null`を返し、各チャンネルはその欄が`null`でないことを個別に確認してから対数尤度計算に加算する。`numericInputs.forEach((el) => el.addEventListener('input', render))`を最終`render()`呼び出し前に配置していることも確認済み
- 判別要素は[apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)の`ITEMS`配列＋`buildChips()`パターンを踏襲。`kind: 'hard'`は`computeCandidateSettings()`でハード除外、`kind: 'soft'`は`TIER_WEIGHT`×出現回数（`SOFT_CAP`で上限3回）を対数尤度に加算するのみ
- field-group-labelは「総G数を共有するチャンネル群」「BB中スイカ契機のULTRA上乗せ（別分母）」「リーチ目役T2のBIG比率（別分母）」で見出しを分け、異なる分母（n）を持つ数値チャンネルは必ず独立した見出しにするというルールを遵守した
