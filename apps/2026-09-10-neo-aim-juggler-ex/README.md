# ネオアイムジャグラーEX 設定判別ツール

「ネオアイムジャグラーEX」（北電子、Aタイプ・ジャグラー系。先代「アイムジャグラーEX」とボーナス確率スペックが完全に同一の後継機種）の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「ネオアイムジャグラーEX」](https://p-town.dmm.com/machines/4801)（2026/05/03更新）と[一撃（1geki.jp）「ネオアイムジャグラーEX」設定判別ページ](https://1geki.jp/slot/s_nijex/0/)に掲載されているブドウ確率・チェリー確率・BIG確率・REG確率の数値データをもとに、二項分布の尤度計算により設定期待度を算出します。

## A-type機種としての特殊な扱いについて

このサイトの他のツール（スマスロ系AT機）は、ストーリー性のある専用の終了画面・エンディング演出・示唆演出（金文字濃厚、虹背景など）を多数搭載しており、それらを②判別要素のチップリストとしてカウントする設計になっている。

しかし「ネオアイムジャグラーEX」はAT・CZ・ストーリー要素の一切ない純粋なAタイプ機種であり、そうした専用の示唆演出は存在しない（プレミアム演出はいずれも出目上「大当り濃厚」を示す直接情報であり、設定を絞り込むための「示唆」ではない。実際に解析サイトでも「プレミア告知は設定差がありません」と明記されていることを確認済み）。そのためこの機種では、②判別要素をチップリストではなく短い説明文のみとし、①数値データにある4つの独立した二項尤度チャンネル（ブドウ確率・チェリー確率・BIG確率・REG確率）による判別を中心に据えている（[マイジャグラーⅤ](../2026-09-10-my-juggler-5/)と同じ設計方針）。これはバグではなく、Aタイプ機種の判別方法の実態に合わせた意図的な設計。

## 機能

- **数値データ**（①）: 通常時総G数を共通の分母として、ブドウ成立回数・チェリー成立回数（ボーナス非同時のみ）・BIG当選回数・REG当選回数の4つを、それぞれ独立した二項尤度チャンネルとして入力可能
  - 空欄の項目は「データなし」として扱われ計算から除外される。0を入力した場合のみ「0回」として計算に反映される（`parseField()`によるnull安全設計）
- **判別要素**（②）: A-type機種のため専用の示唆演出が存在しないことを説明する注記のみを表示。チップリストは意図的に省略している
- 数値データの入力状況に応じて、現在の最有力設定候補をリアルタイム表示
- 広告枠（`.ad-slot`）を3か所設置：ヘッダー直下（728×90）、判別要素と結果の間（300×250）、フッター上（728×90）。今はプレースホルダー表示のみ（詳細はリポジトリルートのREADME「広告の設置について」を参照）

## 一撃（1geki.jp）とのクロスチェック

一撃の設定判別ページには「ボーナス確率」表（BB確率・RB確率・ボーナス合算、公表スペック値）と「ブドウ・チェリー確率」表（実機シミュレーションアプリ全設定TOTAL600万ゲームの実戦値）の両方が、設定1〜6の全設定分そろって掲載されていた。

- BIG確率・REG確率: 一撃の「ボーナス確率」表（設定1＝BIG 1/273.1・REG 1/439.8 〜 設定6＝BIG 1/255.0・REG 1/255.0）は、DMMぱちタウンの機種ページに掲載されている数値と完全に一致することを確認した。信頼性の高いこの公表スペック値をそのまま採用した
- ブドウ確率: DMMぱちタウンの特集記事（[specials/4486](https://p-town.dmm.com/specials/4486)）では「設定1〜5＝1/6.02、設定6＝1/5.78」という集約値が掲載されており、一撃の設定別詳細値（設定1＝1/6.06〜設定5＝1/6.02、設定6＝1/5.80）とほぼ整合していた（実戦シミュレーション値の丸め誤差の範囲内）。設定1〜4の内訳が判明する一撃側の全設定表を採用した
- チェリー確率: DMMぱちタウン側には全設定分の公式表が見当たらなかったため、一撃の実戦シミュレーション値（全設定TOTAL600万ゲーム、チェリーはボーナス非同時当選分）を単独で採用した

### 採用した4チャンネル（ブドウ・チェリー・BIG・REG）と、あえて採用しなかったデータ

課題設計として「合成確率（BIG+REG）」「BIG確率」「REG確率」「ブドウ確率」「チェリー確率」「単独REG確率」のうち、重複しない組み合わせを1つ選ぶ必要があった。今回はマイジャグラーⅤと同様に**BIG確率＋REG確率＋ブドウ確率＋チェリー確率**の4チャンネルを採用し、以下は意図的に不採用とした：

- **合成確率（ボーナス合算）**: BIG確率とREG確率を独立チャンネルとしてすでに採用しているため、合成確率を加えると同じボーナス当選情報を二重にカウントしてしまうため不採用
- **単独REG確率**: DMMぱちタウンの特集記事（[specials/4423](https://p-town.dmm.com/specials/4423)）に「アイムジャグラーEXの参考値」として設定1〜4・設定5-6でグループ化された単独REG確率の表が掲載されていたが、これは通常のREG確率（チェリー重複を含む全REG）とは別の指標であり、かつ設定5・6が同値に集約されておりREG確率単体（全設定で個別の値が判明）より情報量が少ないため不採用とした
- **ピエロ確率・ベル確率**: 全設定共通（設定差なし）とされており、判別要素として意味を持たないため不採用

## データについて

- BIG確率・REG確率・ボーナス合算確率は全設定（設定1〜6）の公表スペック値がDMMぱちタウン・一撃の双方で完全一致しており、信頼度が高い
- ブドウ確率は全設定分の詳細値が一撃側にのみ掲載されており、DMMぱちタウンの集約値（設定1〜5同値・設定6のみ差あり）とも整合していた
- チェリー確率は一撃の実戦シミュレーション値（全設定TOTAL600万ゲーム、ボーナス非同時当選分）のみを採用。DMMぱちタウン側の独立したクロスチェックは取れていない点に留意
- CRITICAL RULE（欠けている設定を絶対に捏造しない）との関係: 本機種はBIG・REG・ブドウ・チェリーのいずれも設定1〜6の全設定分のデータが実在する公開情報から判明したため、[apps/2026-09-06-valvrave-2/](../2026-09-06-valvrave-2/)の`SETTINGS`配列による設定除外パターンは不要だった

## 技術メモ

- [apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)のCSS（白・黒・赤基調のパレット）とHTML骨格（ヘッダー／広告枠／カード①②③／出典／免責事項／フッター、AdSenseスクリプトタグの位置を含む）をそのまま踏襲した単一HTMLファイル。依存ライブラリなし、ビルド不要
- **A-type向けの適応点**: [apps/2026-09-10-my-juggler-5/](../2026-09-10-my-juggler-5/)と同じく、②判別要素はチップリスト方式（`ITEMS`配列＋`buildChips()`）を丸ごと省略し、短い説明文のみに置き換えた。`computeCandidateSettings()`のようなハード除外ロジックも不要となり、`render()`は「4チャンネルの対数尤度を合算してソフトマックス的に正規化する」だけのシンプルな構成にした
- 尤度計算: [apps/2026-09-07-monhun-rise/](../2026-09-07-monhun-rise/)の`render()`にある`parseField(el)`パターンを採用。空欄は`null`を返し、各チャンネルはその欄が`null`でないことを個別に確認してから対数尤度計算に加算する。これにより「入力欄を1つ空欄にしただけなのに0回発生と誤解釈されて、発生確率の高いブドウなどのチャンネルが不当に歪む」という事故を防いでいる
- 4チャンネルとも同じ「通常時総G数」を分母として共有する設計（1geki.jpの設定判別ツールや他の解析サイトの標準的なUIパターンに合わせた）
- フッター直前のフィードバックウィジェット（`.fb-fab`／`.fb-panel`とFormSubmit.co連携スクリプト）は[apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)から変更なしでそのまま流用
