# マイジャグラーⅤ 設定判別ツール

「マイジャグラーⅤ」（北電子/Maruhon、Aタイプ・ジャグラー系の代表機種）の設定判別を助ける計算ツール。[DMMぱちタウンの機種ページ「マイジャグラーV（マイジャグ5）」](https://p-town.dmm.com/machines/4029#anc-point)（2026/09/05更新）に掲載されているブドウ確率・REG確率（単独当選）などの数値データをもとに、二項分布の尤度計算により設定期待度を算出します。

## A-type機種としての特殊な扱いについて

このサイトの他のツール（スマスロ系AT機）は、ストーリー性のある専用の終了画面・エンディング演出・示唆演出（金文字濃厚、虹背景など）を多数搭載しており、それらを②判別要素のチップリストとしてカウントする設計になっている。

しかし「マイジャグラーⅤ」はAT・CZ・ストーリー要素の一切ない純粋なAタイプ機種であり、そうした専用の示唆演出は存在しない（プレミアム演出のトラっぴタッチやレインボーGOGO！ランプはいずれも「大当り濃厚」を示す出目上の直接情報であり、設定を絞り込むための「示唆」ではない）。そのためこの機種では、②判別要素をチップリストではなく短い説明文のみとし、①数値データにある4つの独立した二項尤度チャンネル（ブドウ確率・チェリー確率・BIG確率・REG確率）による判別を中心に据えている。これはバグではなく、Aタイプ機種の判別方法の実態に合わせた意図的な設計。

公開URL: https://haruikntv.github.io/weekly-apps/2026-09-10-my-juggler-5/

## 機能

- **数値データ**（①）: 通常時総G数を共通の分母として、ブドウ成立回数・チェリー成立回数（ボーナス非同時のみ）・BIG当選回数・REG当選回数の4つを、それぞれ独立した二項尤度チャンネルとして入力可能
  - 空欄の項目は「データなし」として扱われ計算から除外される。0を入力した場合のみ「0回」として計算に反映される（`parseField()`によるnull安全設計）
- **判別要素**（②）: A-type機種のため専用の示唆演出が存在しないことを説明する注記のみを表示。チップリストは意図的に省略している
- 数値データの入力状況に応じて、現在の最有力設定候補をリアルタイム表示
- 広告枠（`.ad-slot`）を3か所設置：ヘッダー直下（728×90）、判別要素と結果の間（300×250）、フッター上（728×90）。今はプレースホルダー表示のみ（詳細はリポジトリルートのREADME「広告の設置について」を参照）

## 一撃（1geki.jp）とのクロスチェック

[一撃「マイジャグラー5（マイジャグ5）」設定差・設定判別要素まとめ](https://1geki.jp/slot/s_myj5/0/)（2026/04/28更新）を確認したところ、DMMぱちタウンとほぼ同じ内容のデータが掲載されていた。今回はDMMぱちタウンのブドウ確率・REG確率（単独当選）と、一撃の「設定別ボーナス確率」（BB確率・RB確率・ボーナス合算の公表スペック値）および「ブドウ・チェリー確率（実戦値）」表を突き合わせて採用値を決定した。

- 一撃の「設定別ボーナス確率」表（BB確率・RB確率・ボーナス合算）は、DMMぱちタウンのREG確率（単独当選）の系列とほぼ整合していた（実戦シミュレーション値と公表スペック値の間の小さな誤差の範囲内）。信頼性の高い一撃側の公式スペック値をBIG確率・REG確率としてそのまま採用した
- ブドウ確率・チェリー確率は一撃の「実機シミュレーションアプリ全設定TOTAL600万ゲーム実戦値」を採用（チェリーはボーナス非同時当選分のみのカウント）

### 採用した4チャンネル（ブドウ・チェリー・BIG・REG）と、あえて採用しなかったデータ

課題設計として「合成確率（BIG+REG）」「BIG確率」「REG確率」「ブドウ確率」「チェリー確率」「ボーナス間ゲーム数」のうち、重複しない組み合わせを1つ選ぶ必要があった。今回は**BIG確率＋REG確率＋ブドウ確率＋チェリー確率**の4チャンネルを採用し、以下は意図的に不採用とした：

- **合成確率（ボーナス合算）**: BIG確率とREG確率を独立チャンネルとしてすでに採用しているため、合成確率を加えると同じボーナス当選情報を二重にカウントしてしまうことになるため不採用
- **ボーナス間ゲーム数**: 合成確率（＝ボーナス合算確率の逆数相当）とほぼ同じ情報であり、BIG確率・REG確率と組み合わせると同じ情報の二重カウントになるため不採用
- **ピエロ確率・ベル確率**: DMMぱちタウンの小役確率表によれば、ピエロ・ベルはいずれも全設定共通で1/1024.0であり設定差がないため、判別要素として意味を持たず不採用

## 技術メモ

- [apps/2026-09-06-tokyo-ghoul-slot-checker/](../2026-09-06-tokyo-ghoul-slot-checker/)のCSS（白・黒・赤基調のパレット）とHTML骨格（ヘッダー／広告枠／カード①②③／出典／免責事項／フッター、AdSenseスクリプトタグの位置を含む）をそのまま踏襲した単一HTMLファイル。依存ライブラリなし、ビルド不要
- **A-type向けの適応点**: 参照実装の②判別要素は「金文字濃厚/否定でハード除外」「斜体の示唆で重み加算」というチップリスト方式（`ITEMS`配列＋`buildChips()`）だったが、本機種には示唆演出が存在しないためこの仕組みを丸ごと省略し、短い説明文のみに置き換えた。それに伴い`computeCandidateSettings()`のようなハード除外ロジックも不要となり、`render()`は「4チャンネルの対数尤度を合算してソフトマックス的に正規化する」だけのシンプルな構成にした
- 尤度計算: [apps/2026-09-07-monhun-rise/](../2026-09-07-monhun-rise/)の`render()`にある`parseField(el)`パターンを採用。空欄は`null`を返し、各チャンネルはその欄が`null`でないことを個別に確認してから対数尤度計算に加算する。これにより「入力欄を1つ空欄にしただけなのに0回発生と誤解釈されて、発生確率の高いブドウなどのチャンネルが不当に歪む」という事故を防いでいる
- 4チャンネルとも同じ「通常時総G数」を分母として共有する設計（1geki.jpの設定判別ツールや他の解析サイトの標準的なUIパターンに合わせた）
